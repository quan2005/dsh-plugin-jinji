# 设计决策记录（ADR）

记录本项目的关键架构决策与取舍。每条包含背景、决策、理由与风险。

## ADR-0001：入口按钮采用 DOM 注入而非槽位注册

- **状态**：已接受（2026-08）
- **背景**：期望入口位于左侧栏「新会话」按钮下方。DSH 侧栏官方槽位只有 `sidebar.workspaces` / `sidebar.settings` / `sidebar.footer.action`，New Session 是 shell 私有 DOM，**无官方槽位**（官方手册亦确认）。
- **决策**：用语义后缀选择器 `[class*="_newSession"]` 定位锚点 + `insertAdjacentElement('afterend')` 注入按钮；`MutationObserver` 兜底重建；样式经 `getComputedStyle` 逐属性拷贝内联（幽灵按钮、不硬编码色值）。
- **理由**：
  - 位置精确满足产品需求（与新会话同组）；
  - 计算样式拷贝保证任何主题下与官方按钮像素级一致；
  - 不依赖槽位渲染出口（动态注册的 occupant 曾出现「目录 active 但未渲染」的环境差异）。
- **风险**：依赖 shell 的 CSS Module 语义后缀；官方构建改名需同步。缓解：选择器用 `class*=` 只锚定语义后缀（hash 前缀随构建变）；锚点找不到时按钮不出现、不影响其他功能。

## ADR-0002：面板采用纯 DOM 渲染而非 React 槽位组件

- **状态**：已接受（2026-08）
- **背景**：面板最初注册在 `shell.overlay` 槽位（React 组件）。实测出现「槽位目录 active、组件未挂载」的环境性故障，且动态注册的 occupant 优先级为负、渲染出口行为不可观测。
- **决策**：面板与按钮同机制——`document.createElement` 挂 `document.body`，innerHTML 模板（数据全量 `esc()` 转义）+ 事件二次绑定。
- **理由**：
  - 渲染链路只有 `document` 一个依赖，行为确定；
  - 顺带甩掉了 React 依赖，保持"不依赖任何第三方包"；
  - 动态插件与持久化包两套载体行为完全一致。
- **风险**：需自维护转义与事件绑定纪律（已封装 `esc()`/`renderPanel()` 单一渲染入口）；innerHTML 重绘有轻微性能成本（120 卡片面 <10ms，可接受）。

## ADR-0003：无需编译的分发方式（手写浏览器模块）

- **状态**：已接受（2026-08）
- **背景**：官方浏览器插件都要经过编译工具打包成固定格式（`window.__ModuleLoader__.load`）；独立小项目为此引入一条编译流水线太重。
- **决策**：`lib/client.js` 直接手写成官方同款格式（网页在用到时才执行的模块定义），没有编译工具、没有任何依赖。
- **理由**：这个格式本身很简单（一个工厂函数 + 导出对象），手写可控；打出来的发布包就是最终成品，不需要任何预编译步骤。
- **风险**：没有类型检查和代码压缩；用 `node --check` 语法检查 + 模拟环境自检兜底（见 [development.md](development.md#验证清单)）。

## ADR-0004：面板内容区定位（不遮挡侧栏）

- **状态**：已接受（2026-08）
- **背景**：全屏覆盖遮挡左侧导航，破坏导航连续性（用户明确反馈）。
- **决策**：`position: fixed` 但 `left = 侧栏实测宽度`，打开期间随 resize/DOM 变更重测；点击侧栏任意处自动关闭。
- **理由**：类「设置面板」的打开体验；导航与面板可并存交互。
- **风险**：依赖 `[class*="_sidebarCol"]` 语义后缀测宽（同 ADR-0001 的缓解策略）。

## ADR-0005：日志库根目录三级解析（config > env > cwd）

- **状态**：已接受（2026-08）
- **背景**：早期版本把某台机器上的个人路径（形如 `/Users/<用户名>/Documents/journal`）硬编码在包内，无法公开发布。
- **决策**：`config.root` > `DSH_JINJI_ROOT` > `process.cwd()` 三级解析；包内不带任何机器专属路径。
- **理由**：包保持通用可发布；个人部署通过 profile 的 patch 层覆盖（id 定位替换整行 config）。
- **风险**：cwd 兜底在无 `.journal` 的目录启动时返回 `no-journal`（面板显示加载失败，行为明确）。

## ADR-0006：文件读写走官方 `fs` 服务，不用 Node 自带文件接口

- **状态**：已接受（2026-08）
- **背景**：在 DSH 里做文件访问，应该尊重官方的沙箱与权限策略，而不是绕过它们。
- **决策**：服务端部分声明依赖 `fs` 服务，所有文件操作都走它的 `resolve/listDir/readText/contains` 方法。
- **理由**：沙箱策略层可以整体替换（比如换成远程沙箱后本插件无需改动）；路径防护直接做在官方服务之上。
- **风险**：如果 `fs` 服务还没就绪，插件会先等待（声明依赖的默认行为），不会出现半初始化状态。

## ADR-0007：记忆系统采用 summary 分层加载（写时带摘要，读时先读摘要）

- **状态**：已接受（2026-08）
- **背景**：日志库会持续增长（数百条日志、数十个画像）。若每次浏览都读全文，成本随库大小线性膨胀；但用户浏览时首先需要的是「整张记忆地图」，而不是每条全文。
- **决策**：写入时由 AI 在每条记录头部写下 `summary`；读取时分两层——索引层只解析全部 summary（恒定小成本），全文层按需读取被点开的单条。此模式与 DSH 技能目录的「先 name/description、调用时再加载全文」同构。
- **理由**：
  - 一次整理，多次廉价读取：summary 的撰写成本在记录时付清，之后任意规模的库都只需几十 KB 索引；
  - 语义判断（写什么、怎么归纳、何时更新）全部留在模型侧，代码层保持极简、零语义理解；
  - 同一份 summary 同时服务面板浏览与启动时的记忆快照。
- **风险**：summary 质量依赖 AI 的整理纪律（已在写入约定中要求「结论先行、有信息量」）；摘要过时需由会话在追加/更新时同步维护。

## ADR-0008：记忆分两轨——流水记忆 + 画像记忆（实体提炼）

- **状态**：已接受（2026-08）
- **背景**：单纯的流水日志能回答「发生了什么」，却无法直接回答「这个人 / 这个产品是什么样的」；后者需要跨时间、跨事件的归纳。
- **决策**：记忆分两轨。流水记忆（日志）记录事件流；画像记忆（画像档案）把人物与产品提炼成**独立的实体画像**，每个实体一份档案，渐进式更新（建档 → 补全 → 深挖）。画像由 AI 在整理素材的过程中从流水里持续提炼。
- **理由**：
  - 实体画像把散落各条日志里的信息收敛成完整形象，是对记忆的二次压缩；
  - 画像反哺后续事件的理解（遇到同一实体先读画像），形成「事件滋养实体、实体反哺事件」的循环；
  - 这是与其他单轨记忆系统（纯流水 / 纯事实检索）最大的差异点。
- **风险**：提炼质量依赖 AI 的归纳纪律（建档门槛、渐进深挖规则需在写入约定中固化）；画像与流水可能不一致时，以最新事件为准并回写画像。

## ADR-0009：启动摘要注入采用「异步预计算 + 同步提供器」

- **状态**：已接受（2026-08）
- **背景**：需要把记忆摘要作为运行时上下文在会话启动时注入（systemPrompt 动态上下文）；但该提供器签名是同步返回字符串，而文件读取走 `fs` 服务是异步的。
- **决策**：在 `agent/session-start` 事件里异步预计算快照（`composeSummary`），按会话缓存（WeakMap）；上下文提供器只同步读取缓存。快照按会话只算一次（SessionStart 语义）。
- **理由**：
  - 保持「文件访问全走 `fs` 服务」的既有约束（ADR-0006），不为注入开同步文件后门；
  - 会话启动到首个用户请求之间通常有充足时间，异步预计算几乎总能在首个请求前完成；
  - 即使未完成，降级只是「该次请求暂无摘要」，后续组装自动补上，无失败模式。
- **风险**：极短会话（启动即请求）可能错过首个请求的摘要；预计算失败时静默降级为空快照（可接受，浏览面板不受影响）。

## ADR-0010：用注入的书写规范实现「主动记录」

- **状态**：已被 ADR-0012 取代（2026-08）——全局注入移除，书写规范改由 Agent 预设承载；本记录保留作为演进背景
- **背景**：只注入摘要，AI 会读记忆但不会主动写——「读与写」缺一半。此前 jinji agent preset 用技能文件承载书写约定，preset 删除后主动记录随之消失。
- **决策**：插件在 Host 侧再注册一个 systemPrompt 上下文 `jinji:memory-protocol`（顺序 135，排在摘要之后），把书写规范（何时写、日志/画像怎么写、frontmatter 约定、建档门槛）作为纯文本注入每个会话；写入由模型用自己的文件工具完成，插件不注册写接口、不替模型写。
- **理由**：
  - 与摘要注入共用同一条「会话启动预计算 + 同步提供器」链路，零新增服务、零新增依赖；
  - 格式契约（路径、frontmatter）由插件统一维护，任何装了插件的 DSH 会话都按同一套约定写，保证写出来的文件能被面板与摘要正确读取；
  - 语义判断（什么值得记、怎么归纳）留在模型侧，与「大模型为核心驱动」的定位一致；
  - 这是 preset 时期已被验证有效的机制（指令注入），移植成本最低。
- **风险**：注入规范 ≠ 必然执行，写与不写仍取决于模型在会话中的判断；若会话环境没有文件写入工具，规范无法落地（属于环境能力问题，非本插件可解）。缓解：规范写明触发时机并给出「写完后自查」清单，提高执行率。

## ADR-0011：插件配置走自建卡片 + 插件自有配置文件，绕开 settings 命名空间白名单

- **状态**：已接受（2026-08）
- **背景**：DSH「设置 → 插件配置」页的卡片槽位（`settings.plugin.item`）对所有带浏览器部分的插件开放，但卡片背后的 settings 命名空间由 Host 白名单硬编码（`shell` / `agent-loop` / `web-search-deepseek`）——第三方插件的命名空间只会得到 `settings-not-exposed`，无法用官方 settings 通道持久化配置。
- **决策**：浏览器部分注册自己的卡片进 `settings.plugin.item`（用 shell 共享的 React，`require('react')`，非本包依赖）；读写走插件自己的数据路由 `GET/POST /api/jinji-memory?action=config`；持久化到记忆根目录下的 `.jinji-memory.json`（`fs.writeText` 原子写）。生效优先级：配置文件 > cordis config > 内置默认；`root` 例外，只在 cordis config / 环境变量里配。
- **理由**：
  - 用户得到与内置插件一致的原生设置体验，又不要求改动 DSH 本体；
  - 配置文件放在记忆根目录下，随记忆库一起迁移备份，语义自洽；
  - 写入仍走 `fs` 服务（ADR-0006 的约束不破），逐字段校验后才落盘；
  - 提供器每次组装实时读生效配置，保存后新会话立即生效，免去重启。
- **风险**：绕开了官方 settings 的分层/审计语义（覆盖标记、并发闸门都没有）；`settings.plugin.item` 槽位或 shell 共享模块表（react）在未来版本变化时卡片静默消失（按钮与面板不受影响）。

## ADR-0012：书写规范从全局注入迁往 Agent 预设（用户自选）

- **状态**：已接受（2026-08）
- **背景**：ADR-0010 把书写规范作为 systemPrompt 上下文全局注入，每个会话的提示词都带一份「使用说明」——但大多数会话并不需要记东西，全局注入是噪声；用户明确希望「做成 preset 让用户自主选择」。
- **决策**：移除 `jinji:memory-protocol` 全局上下文与 `writeProtocol` / `writeProtocolEnabled` 配置字段；书写规范改由 Agent 预设「谨迹秘书」的 persona 段落承载。预设在运行期经 roster 官方通道安装：`copy('standard', 'jinji', '谨迹秘书')` → persona 行整段替换为秘书人设（`{{model}}` / `{{cwd}}` 模板变量保留，`__MEMORY_ROOT__` 替换为实际根目录）→ 写 `preset.yml` → `standingKeyFor` 挂载校验。安装入口在设置卡片（`POST /api/jinji-memory?action=install-preset`）。
- **理由**：
  - preset 是 DSH 原生的「按需选择能力」机制：用户建新会话时显式选择，普通会话的提示词保持干净；
  - bundle 无法声明式地带一个 preset——patch 的 `!!js` 表达式在 profile 目录语境求值，拿不到包内路径；roster 的 `copy()` 是唯一官方创作通道，且复制自当前 standard，与宿主版本天然兼容；
  - 预设落在用户 preset 根目录（普通文本文件）：可直接编辑规则、可在「Agent 预设」页删除，完全可逆；
  - persona 段落在 agent 生命周期内前缀稳定（dsh-persona 的设计），KV-cache 友好。
- **风险**：preset 复制的是安装时刻的 standard——DSH 大版本升级 standard 后副本不会自动跟进（删除重装即可）；卸载插件不会移除已安装的预设（它脱离插件也能运行，但规则文本失去更新来源）；standard 的 persona 行结构变化（改 id 或删除该行）会让安装报错而非静默装错。
